# Corrección administrativa del correo comunitario

Estado: IMPLEMENTED localmente; validación de integración PARTIAL en PostgreSQL desechable.

Objetivo: permitir que un administrador autorizado corrija el correo de una cuenta comunitaria pendiente tras verificar institucionalmente la identidad. La constancia registra el método y el administrador, no evidencia documental ni fotografías. La verificación real se realiza fuera del sistema.

Alcance: consulta exacta por identificación de cuentas pendientes; corrección bajo roles y capacidades existentes; actualización condicional serializable, invalidación de tokens comunitarios, emisión de un token y auditoría en la misma transacción. El envío se intenta después del commit; si falla, el reenvío existente permite recuperación. PATCH general no puede cambiar correo mientras la cuenta esté pendiente. No se cambian afiliaciones ni pantallas administrativas.

API: GET /community-accounts/pending?identification=... requiere rol Administrador y usr.users.read. POST /community-accounts/:id/correct-email requiere rol Administrador y usr.users.update; acepta email, identityVerified=true y verificationMethod IN_PERSON o INSTITUTIONAL. El sistema no comprueba por sí mismo la identidad. No registrar identificaciones en logs HTTP ni almacenar documentación sensible.

Persistencia: se prepara un índice único funcional sobre lower(btrim(email)) para cerrar carreras con otras escrituras. No modifica filas, pero fallará si existen duplicados normalizados: es obligatorio revisar y resolver esas colisiones mediante un plan aprobado antes de desplegarlo. El índice funcional no está representado en el esquema Prisma y debe preservarse en futuras migraciones. También sigue pendiente la migración de nombres de la etapa 1. No ejecutar migraciones en bases compartidas sin autorización. Reversión: retirar el índice solo mediante migración aprobada; tras una corrección, no restaurar tokens anteriores. La recuperación de datos requiere el procedimiento de respaldo aprobado.

Pruebas: PostgreSQL desechable con credenciales y datos sintéticos: registro, activación, tokens, duplicados, corrección, auditoría, fallo y reintento de entrega, compatibilidad con token histórico y carreras activación/corrección y reenvío/corrección. Se aplicaron ambas migraciones en una base vacía y se comprobó con datos sintéticos que el índice rechaza duplicados normalizados. HTTP con guards y persistencia reales: 401, 403, login pendiente y corrección autorizada. El proveedor de correo fue simulado. La suite antigua permanece bloqueada porque elimina datos sin verificar destino.

Riesgos: hasta aplicar el índice propuesto, la comprobación insensible en transacción serializable no garantiza unicidad frente a escrituras concurrentes ajenas. Su aplicación puede fallar por datos históricos y afecta a todas las cuentas. Los ensayos de concurrencia no prueban todas las intercalaciones posibles. El correo real depende de configuración externa y permanece NOT_VERIFIED. Una constancia administrativa no prueba que la verificación institucional se realizó correctamente. CU V2 relacionados: NOT_VERIFIED hasta localizar y validar el catálogo inmutable; no se inventan identificadores. Especificación histórica propuesta contrastada con el contrato funcional actualizado del usuario.
